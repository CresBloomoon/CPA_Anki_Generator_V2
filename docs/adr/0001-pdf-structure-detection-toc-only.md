# ADR 0001: PDF構造検出をTOCベース・可変階層方式に変更し、最低カード枚数の自動算出を撤去する

## ステータス

Accepted（Phase2-1で採用・実装）

## コンテキスト

実装依頼書および当初のPhase2-1計画では、旧`pdf_parser.py`のアプローチ（ページ上部30%の
視覚的見出し検出＋TOC/outlineをフォールバックとして併用、「章→節」の固定2階層、ランク
タグ（短答A／論文B等）のカウントによる最低カード枚数の自動算出）を踏襲する前提だった。

Phase2-1実装後、実際にインプットする予定のPDF7冊分（企業法・監査論・管理会計論×2・
財務会計論×3）の`doc.get_toc()`生データを確認したところ、以下が判明した。

1. **「章→節の2階層」という前提が科目によって成立しない**。企業法・監査論は章→節の
   2階層で想定通りだが、管理会計論は節という単位自体が存在せずフラット1階層、
   財務会計論は「部→章」という異なる粒度の2階層だった。
2. **TOC（しおり）は全7ファイルで確実に整備されており、内容も正確**だった。旧実装が
   視覚的検出を「主」・TOCを「フォールバック」としていた設計上の前提が、少なくとも
   実際に使う教材では成立しない（むしろ逆で、TOCの方が一貫して信頼できる）。
3. **最低カード枚数の自動算出は実運用で使われていなかった**。開発者へのヒアリングにより、
   実際の運用では常に手動で上書きされており、機能として形骸化していたことが判明した。
   （視覚的検出ロジック自体、標準教科書の装丁を前提にした複雑な設計であり、個別配布の
   レジュメ形式の教材には機能していなかった。）
4. **同一タイトルが複数回出現するケースがある**（例：財務会計論の「第１部」と「第２部」に
   同名の章が両方存在する）。「部」という階層を吸収しない限りタイトルだけでは区別できない。

これらは実データを見て初めて判明したものであり、実装依頼書作成時点では想定されていな
かった。

## 決定

1. **PDF構造検出はTOC（`doc.get_toc()`）のみを情報源とする**。ページ上部の視覚的見出し
   検出（`_find_visual_header`）およびTOCとの突合・フォールバック統合ロジック
   （`_merge_toc_fallback`）は全廃した。
2. **「章」「節」という固定ラベル・固定階層を前提にしない、可変階層のancestors方式**を
   採用する。`doc.get_toc()`が返すフラットな`(level, title, page)`列を1回走査し、
   「現在各レベルで直近に見たタイトル」を保持する辞書から各エントリの祖先タイトル列
   （`ancestors: tuple[str, ...]`）を組み立てる。階層数（1階層／2階層／それ以上）や
   単位の呼び方（章／節／部／編）を一切コードで仮定しない。
3. **TOCの全エントリを無条件でセクション候補として出力する**。目次・はじめに等のノイズ
   エントリの自動除外や、同一タイトルの重複除去は行わない。人間がテーブルのチェック
   ボックスで選別する運用とする。同一タイトルの衝突は`ancestors`が異なることで自然に
   区別できる。
4. **`min_card_count`（最低カード枚数の自動算出）を、ドメイン層・リポジトリ層の両方から
   完全に撤去する**。`Section.min_card_count`、`RawSection.min_card_count`、
   `_count_ranks_in_text`、関連する正規表現を削除した。
5. 上記に伴い、`Section.chapter_title`（固定1階層を前提にしたフィールド）も削除した。
   デッキパスは`ancestors`と`title`からusecase層（Phase3-1）が組み立てる。
6. `PageRange`のバリデーションを`end_page <= start_page`（エラー）から
   `end_page < start_page`（エラー、ただし等しい場合＝ゼロ長レンジは許容）に緩和した。
   実データで「部の見出しとその次のエントリが同一ページから始まる」ケースが複数確認され
   たため、これは異常値ではなく正当なケースとして扱う必要がある。
7. TOCのページ番号が前のエントリより逆行しているような不正なデータに遭遇した場合は、
   例外を送出してスキャン全体を失敗させるのではなく、該当エントリの`end_page`を`None`
   （終端不明）にフォールバックし、`ScanResult.warnings`に記録する。

## 結果・影響

- `_kanji_to_arabic`（漢数字→算用数字変換）も削除した。7ファイル全エントリを確認した
  結果、漢数字表記のタイトルが1件も存在しなかったため。ただし将来的に漢数字タイトルを
  持つ教材が来た場合に備え、`_normalize_title`は「先頭が`第<算用数字><章/節/部/編/項/款>`
  という形にマッチしない場合はタイトルをそのまま返す」設計にしており、クラッシュしない
  ことをテストで保証している。
- 全角・半角混在の数字表記（例：「第１章」〜「第９章」は全角、「第10章」以降は半角、と
  いう混在が全科目で共通して見られた）は引き続き正規化し、ゼロ埋め（`第04章`等）する。
  財務会計論は第24章まで存在するため、ゼロ埋めをしないとAnkiのデッキ一覧で並び順が
  崩れる（"第1章"の次に"第10章"〜"第19章"が来てしまう）実害が具体的に確認できた。
- Phase1-1で実装済みの`Section`ドメインエンティティに変更が生じ、既存のテスト
  （`test_section.py`、`test_generation_job.py`のヘルパー）を修正する必要が生じた。
- Phase5-2で予定していたセクション編集テーブルの「章タイトル」列は、この設計変更により
  不要になる可能性が高い（`ancestors`を使った出力デッキ名の自動組み立てで階層情報は
  表現できるため）。テーブルの最終的な列構成はPhase5-2着手時に改めて検討する。
- 依頼書の「最低限作成されるカード枚数」列は、本ADRの決定によりスコープから外れる。
  カード生成の完全性（すべての論点をカード化すること）は、AIプロンプト
  （`project_constitution.md`等）側の指示のみで担保する。

## 検証

実装は`docker compose run --rm backend sh -c "pip install -e .[dev] && pytest"`で
54件のテストが全てパスすることを確認済み（ドメイン層・リポジトリ層のユニットテストに
加え、`doc.set_toc()`で組み立てた実PDFに対するエンドツーエンドテストを含む）。実際の
7冊のサンプルPDFに対する`scan()`の目視確認はPhase6-2のE2E検証で改めて実施する。
