# Phase7-2-3: 再起動後の読み込み対応

## 背景

Phase7-2-1・7-2-2で、`GenerationJob`を`GenerationJobRepository`経由でJSON
ファイルに保存する仕組み（セクション完了時・ブロック完了時のsave()）までは
実装済みだったが、「読み込み」の経路が無く、バックエンドを再起動すると
メモリ上の`JobStore`が空になり、ディスク上のJSONは無事でも該当job_idへの
アクセスが404になっていた。本Phaseはこのギャップを埋める。

現状把握の結果、`job_id`起点のジョブ取得は`JobStore.get()`（`GetGeneration
JobStatusUsecase.execute()`経由）1箇所に集約されており、進捗確認API・
ジョブ全体ダウンロード・セクション単位ダウンロードの3ルートすべてがこれを
通ることを確認済み。この1箇所にフォールバックを実装すれば、3ルート全てに
一括で反映される。

## 何を実装したか

- `backend/app/repositories/jobs/job_store.py`（修正）
  - `get()`を「メモリを見る→無ければ（リポジトリが設定されていれば）
    `GenerationJobRepository.get()`を試す→見つかればメモリにも載せてから
    返す→どちらにも無ければ`JobNotFoundError`」というロジックに変更した
  - ディスクから読み込んだジョブをメモリに載せる際、`GenerationJob
    Repository.save()`は呼ばない（今読んだばかりの同じファイルへの
    無駄な再書き込みを避けるため）。`self._jobs[job_id] = job`と直接
    辞書に代入するだけに留めている
  - ロックは`get()`全体（ディスク読み込みを含む）を`self._lock`の中で
    行う。`save()`と同じ粒度で対称的にした
  - クラスの説明コメントを、「in-memory storage」から「メモリ優先＋
    ディスクフォールバック」という実態に合わせて更新した
- `backend/tests/repositories/jobs/test_job_store.py`（修正）
  - `TestFallbackToRepository`クラスを新設し、以下を検証：
    メモリに無い`job_id`がリポジトリから読み込めること／2回目の`get()`
    ではリポジトリを再度読みに行かないこと（`_SpyGenerationJobRepository`
    で呼び出し回数を計測）／メモリにもリポジトリにも無い場合は
    `JobNotFoundError`になること
  - 既存の`test_get_still_reads_from_the_in_memory_dict_not_the_repository`
    はアサーション・挙動は変更せず、コメントのみ「フォールバック自体は
    存在するが、メモリヒット時は一切リポジトリに触れない」という現状に
    合わせて更新した
- `backend/tests/routes/test_generation_routes.py`（修正）
  - `TestPersistenceAcrossRestart`クラスを新設し、HTTPレベルの統合テスト
    を追加。実際に2つの`JobStore`インスタンス（「再起動前」「再起動後
    （空のメモリ、同じ`GenerationJobRepository`を共有）」）を用意し、
    再起動後も進捗確認・ジョブ全体ダウンロード・セクション単位ダウンロード
    の3エンドポイントがいずれも200を返すことを確認した

## 実装中に発見したバグ・問題点

なし。

## 大きな判断とその理由

- **フォールバックを`JobStore.get()`自体に実装した（`GetGenerationJob
  StatusUsecase`側では実装しなかった）**：`save()`が既に「メモリ更新＋
  （設定されていれば）ディスク書き込み」という対称的な二重責務を持って
  いるため、`get()`に「メモリ参照＋（無ければ）ディスク読み込み」を
  持たせるのが設計として対称的だった。usecase側で実装する案も検討したが、
  ディスクから読んだジョブをメモリに載せ直す際に`JobStore`の公開APIが
  `save()`しか無く、それを呼ぶと同じファイルへの無駄な再書き込みが
  発生してしまう。結局`JobStore`側に「メモリにだけ載せる」内部処理を
  持たせる必要が出るため、素直に`JobStore.get()`に閉じ込めることにした
- **フォールバックで読み込んだジョブは、リポジトリへの書き戻しをしない
  設計にした**：今読んだばかりの内容をそのまま同じファイルに書き戻しても
  意味がなく、無駄なディスクI/Oになるだけのため
- **HTTPレベルの統合テスト（`TestPersistenceAcrossRestart`）を追加した**：
  `JobStore`単体のテストに加えて、実際に「進捗確認・ダウンロード両APIが
  再起動後も動く」というPhase7-2-3の目的そのものを、ルート層まで含めて
  直接検証しておきたかったため。2つの`JobStore`インスタンスを名前付き
  変数として用意し（依存性オーバーライドのlambda内で毎回新規生成する
  のではなく）、「再起動前は1つの同じインスタンスを全リクエストが共有する」
  という実プロセスの単一シングルトンの挙動を正しく再現している

## スコープ外として明記した点（引き続き未対応）

再起動の瞬間に`RUNNING`だったセクションが、そのままディスクに凍結されて
残り続ける問題（後片付けをするはずだったバックグラウンドスレッドが
旧プロセスと一緒に消えるため）は、本Phaseでも対応していない。このセクション
は読み込みはできるが、`DONE`/`PARTIALLY_DONE`以外はダウンロード不可
（`SectionNotDownloadableError`）のまま、再試行・クリアする手段も無い
状態で残る。対応するかどうかは別途判断する。
